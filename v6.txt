Бележка за продължаване — StudentManagement
1. Главна цел на проекта
Целта е постепенно да изградим Student Management System, като започнем от Students CRUD и надграждаме системата с:
1.	👨‍🎓 Students — добавяне, преглед, редактиране и изтриване
2.	🔍 Search — търсене на студент
3.	📚 Courses / Subjects — предмети
4.	📝 Grades — оценки
5.	📊 Average Grade — автоматично изчисляване на среден успех
6.	📅 Attendance — присъствия
7.	👤 Student Details — подробна страница за студент
8.	🎨 По-добър интерфейс
9.	💾 Database — текущата база вече е настроена и се използва
10.	🔐 Login / Roles — ако решим системата да има администратор и потребители
Основен архитектурен принцип
Изграждаме проекта постепенно, без предварително да създаваме ненужна сложност.
Всяко решение трябва:
•	да работи добре за текущата функционалност;
•	да позволява спокойно добавяне на следващите функционалности;
•	да не налага ненужни patterns само „защото са patterns“.

7. Какво разгледахме за EF Core
Разгледахме подробно:
•	Add()
•	SaveChangesAsync()
•	FindAsync()
•	Update()
•	Remove()
•	Change Tracking
•	Unchanged
•	Modified
•	Deleted
Важно разграничение:
_context.Students.Add(student);
не означава, че студентът вече е записан в Database.
Реалното записване става при:
await _context.SaveChangesAsync();
Схемата е:
Student object
      ↓
DbSet.Add()
      ↓
Change Tracker
      ↓
SaveChangesAsync()
      ↓
EF Core
      ↓
SQL INSERT
      ↓
Database

12. Решения, които вече сме взели
Service Pattern — ДА
Използваме:
Controller
    ↓
IStudentService
    ↓
StudentService
Controller-ът не трябва да съдържа database/business logic.
________________________________________
Интерфейси — отделна папка
Използваме:
Services
└── Interfaces
Това е умишлено решение, за да бъде структурата ясна.
________________________________________
Repository Pattern — ЗАСЕГА НЕ
Обсъдихме Repository Pattern.
Решението е:
Не добавяме Repository само заради самия pattern.
Причината е, че проектът е сравнително малък, а EF Core вече предоставя data-access abstraction чрез:
DbContext
DbSet
Ако проектът порасне и се появи реална необходимост, Repository може да бъде добавен по-късно.
________________________________________
CSV / TXT Export
Ако по-късно поискаме:
Database
    ↓
CSV / TXT
не е задължително да използваме Repository.
По-логично е да имаме отделна export функционалност/service.
________________________________________
MySQL / друга Database
Ако по-късно сменим SQL Server с MySQL или друг provider, първо оценяваме реалната нужда от промяна в архитектурата.
EF Core поддържа различни database providers.
Repository не се добавя автоматично само защото сменяме Database.
________________________________________
13. Бъдещи връзки в Database
В момента Student не трябва да се разглежда като напълно изолирана таблица.
При Grades например очакваме връзка от типа:
Student
   │
   │ 1
   │
   │ *
   ▼
 Grade
При Courses и Grades постепенно ще проектираме връзките между:
             Student
             /     \
            /       \
           ▼         ▼
       Course       Grade
                     │
                     ▼
              Average Grade
Точната Database структура ще бъде уточнена, когато стигнем до тези функционалности.

14. Как пишем проекта
Това е много важно.
Правило №1 — Стъпка по стъпка
Не правим 10 промени наведнъж.
Работим така:
1 малка промяна
      ↓
обяснение
      ↓
потребителят я прави
      ↓
Build
      ↓
проверка
      ↓
следваща стъпка
________________________________________
Правило №2 — Не гадаем кода
Ако трябва да променим съществуващ файл:
Потребителят изпраща файла
            ↓
Разглеждаме реалния код
            ↓
Обясняваме какво трябва да се промени
            ↓
Правим конкретната малка промяна
Особено важно за:
Controller
Service
View
ViewModel
DbContext
________________________________________
Правило №3 — Обяснение на начинаещо ниво
Не просто:
„Копирай този код.“
Обясняваме:
•	какво прави кодът;
•	защо го правим;
•	кой слой отговаря за него;
•	какво се случва с данните;
•	как EF Core комуникира с Database.
________________________________________
Правило №4 — Обясненията са под кода
Например:
var student = await _studentService.GetByIdAsync(id);
След кода:
Service-ът търси студента по неговото ID.
Не натъпкваме излишни коментари вътре в кода.
________________________________________
Правило №5 — Използваме блок-схеми
При архитектурни и EF Core концепции използваме схеми.
Например:
Controller
    ↓
Service
    ↓
EF Core
    ↓
DbContext
    ↓
SQL Server
    ↓
Database
При Create:
Create()
    ↓
CreateAsync()
    ↓
DbSet.Add()
    ↓
Change Tracker
    ↓
SaveChangesAsync()
    ↓
SQL INSERT
    ↓
Database
________________________________________
Правило №6 — Build след логична малка промяна
След всяка логична малка промяна проверяваме:
Build succeeded

Errors: 0
Warnings: 0
Едва тогава продължаваме.
________________________________________
Правило №7 — Security
По време на разработката обръщаме внимание на:
✓ SQL Injection
✓ Validation
✓ Whitespace
✓ MaxLength
✓ XSS
✓ Mass Assignment
✓ CSRF
✓ Authorization
✓ Database constraints
Вече обсъдихме, че нормалните LINQ заявки на EF Core са параметризирани и не трябва да сглобяваме SQL чрез string concatenation.

Ключово правило
