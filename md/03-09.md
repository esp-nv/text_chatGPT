# **<mark>12. Решения, които вече сме взели</mark>** 

## **<mark>Service Pattern — ДА</mark>** 

<mark>Използваме:</mark> 

```
Controller
```

```
    ↓
IStudentService
    ↓
StudentService
```

<mark>Controller-ът не трябва да съдържа database/business logic.</mark> 

## **<mark>Интерфейси — отделна папка</mark>** 

<mark>Използваме:</mark> 

```
Services
└── Interfaces
```

<mark>Това е умишлено решение, за да бъде структурата ясна.</mark> 

## **<mark>Repository Pattern — ЗАСЕГА НЕ</mark>** 

<mark>Обсъдихме Repository Pattern.</mark> 

<mark>Решението е:</mark> 

**<mark>Не добавяме Repository само заради самия pattern.</mark>** 

Причината е, че проектът е сравнително малък, а EF Core вече предоставя data-access abstraction чрез: 

```
DbContext
DbSet
```

Ако проектът порасне и се появи реална необходимост, Repository може да бъде добавен по-късно. 

## **<mark>CSV / TXT Export</mark>** 

<mark>Ако по-късно поискаме:</mark> 

```
Database
```

```
    ↓
CSV / TXT
```

<mark>не е задължително да използваме Repository.</mark> 

<mark>По-логично е да имаме отделна export функционалност/service.</mark> 

## **<mark>MySQL / друга Database</mark>** 

Ако по-късно сменим SQL Server с MySQL или друг provider, първо оценяваме реалната нужда от промяна в архитектурата. <mark>EF Core поддържа различни database providers.</mark> 

<mark>Repository не се добавя автоматично само защото сменяме Database.</mark> 

# **<mark>13. Бъдещи връзки в Database</mark>** 

В момента Student не трябва да се разглежда като напълно изолирана таблица. 

<mark>При Grades например очакваме връзка от типа:</mark> 

```
Student
   │
   │ 1
   │
   │ *
   ▼
 Grade
```

<mark>При Courses и Grades постепенно ще проектираме връзките между:</mark> `Student /     \ /       \ ▼         ▼ Course       Grade │ ▼ Average Grade` 

Точната Database структура ще бъде уточнена, когато стигнем до тези функционалности.
