3. Какво показва за аналитичното ти мислене?
Бих разграничил три способности.
А. Да виждаш системата като цяло
Вместо да мислиш само за студентите като записи в база данни, разглеждаш учебни програми, модули, курсове, конкретни провеждания на курсове и записвания.
Това е правилна посока. Например Course и CourseOffering не е задължително да са едно и също: курсът описва учебната единица, докато конкретното провеждане може да има период, преподавател, капацитет и записани студенти.
Точно такива разграничения са важни при моделирането на реални бизнес процеси.
Б. Да мислиш за проблеми, преди да са възникнали
Обмисляш какво се случва при грешни входни данни, неуспешно записване, ограничения в базата и бъдещо добавяне на функционалности.
Това е полезен навик. Един добър разработчик не пита само „Как да реализирам функцията?“, а и:
•	Какво става, ако данните са невалидни?
•	Какво става, ако две операции се случат едновременно?
•	Какво става, ако записването в базата се провали?
•	Как ще разберем какво е станало след възникване на проблема?
•	Как ще променим функционалността след шест месеца?
Тези въпроси се виждат в посоката на твоите записки.
В. Да знаеш кога да не усложняваш системата
Тук според мен е най-голямата възможност за развитие.
В UI/UX концепцията например се разглеждат два стандартни интерфейса и персонализиран интерфейс, настройки за подредба, drag-and-drop, теми, табове и различни визуални състояния. Това е интересно като идея, но представлява голям обем работа.

8. Важен въпрос: как да покажеш собствените си инженерни умения?
Ще го кажа директно: ако използваш AI помощ при проектирането и ученето, това само по себе си не е проблем. Но трябва да можеш да обясниш решенията, които приемаш, и да проверяваш дали са правилни.
За всяко важно решение опитай да можеш да отговориш на пет въпроса:
22.	Какъв проблем решавам?
23.	Защо избрах този подход?

Същото важи за тестовете: трябва да можеш да покажеш тест, който преди поправката се проваля и след нея преминава.
Това ще бъде много по-силно доказателство за твоите умения, отколкото обемът на документацията.

1. Generics — общ механизъм за различни типове
Да предположим, че системата управлява материали, оборудване и животни. Не искаш да пишеш три почти еднакви реализации за операции, които имат обща логика.
С Generics можеш да дефинираш общ договор:
csharp
public interface IEntity<TId>
{
    TId Id { get; }
}

public interface IRepository<TEntity, TId>
    where TEntity : IEntity<TId>
{
    Task<TEntity?> GetByIdAsync(
        TId id,
        CancellationToken cancellationToken = default);

    Task AddAsync(
        TEntity entity,
        CancellationToken cancellationToken = default);
}
Тук TEntity и TId са параметри на типове. Когато използваш интерфейса, можеш да посочиш конкретните типове:
csharp
public class Material : IEntity<Guid>
{
    public Guid Id { get; init; }
    public string Name { get; set; } = string.Empty;
}

public class Equipment : IEntity<Guid>
{
    public Guid Id { get; init; }
    public string Name { get; set; } = string.Empty;
}
И двата типа могат да използват обща реализация на repository, защото отговарят на един и същ договор.
Какво печелиш?
•	По-малко дублиране на инфраструктурен код.
•	Проверка на типовете по време на компилация.
•	Възможност да добавяш нови модели, без да копираш еднакви CRUD операции.
Има обаче важна граница: Generics не правят автоматично бизнес логиката универсална. Material може да се измерва в килограми, а Equipment да има индивидуален сериен номер. Тези правила не трябва да се заличават само защото и двата типа имат Id.
2. int?, HasValue и nullable типовете — когато стойността не е задължителна
Представи си, че потребителят създава конфигурация за нов тип обект.
За някои обекти количеството може да бъде задължително, а за други може да няма смисъл. Или дадено ограничение може да бъде зададено едва на по-късен етап.
csharp
public class ObjectDefinition
{
    public string Name { get; set; } = string.Empty;

    public int? MaximumQuantity { get; set; }
}
int? означава, че стойността може да бъде цяло число или null.
csharp
if (definition.MaximumQuantity.HasValue)
{
    int maximum = definition.MaximumQuantity.Value;

    // Проверка спрямо зададения лимит.
}
else
{
    // Не е зададен лимит.
}
В съвременния C# често е по-удобно да използваш pattern matching:
csharp
if (definition.MaximumQuantity is int maximum)
{
    // Тук maximum вече е обикновен int.
}
Това е полезно, когато конфигурацията позволява незадължителни стойности.
Но внимавай: null трябва да има ясно значение. Той може да означава „не е зададено“, но не бива произволно да означава и „нула“, и „неограничено“, и „неизвестно“.
Например при наличност:
•	0 означава, че наличността е нула;
•	null може да означава, че наличността не е изчислена или не е приложима;
•	„неограничена наличност“ е отделно бизнес правило.
Това разграничение е особено важно за системата ти.
3. TryParse — безопасно преобразуване на динамични данни
Това според мен е една от най-пряко приложимите техники за твоята идея.
Ако потребителят може да дефинира атрибути като „Тегло“, „Брой“, „Температура“ или „Срок на годност“, може да се наложи стойностите да идват от формуляри като текст.
Например:
csharp
string input = "125";

if (int.TryParse(input, out int quantity))
{
    // quantity е 125
}
else
{
    // Въведената стойност не е валидно цяло число.
}
За десетични числа е добре да вземеш предвид културата, защото в различни среди десетичният разделител може да е , или ..
csharp
using System.Globalization;

string input = "12,5";

if (decimal.TryParse(
        input,
        NumberStyles.Number,
        CultureInfo.GetCultureInfo("bg-BG"),
        out decimal weight))
{
    // weight е 12.5
}
В универсалната ти система бих създал централен механизъм за преобразуване и проверка на стойности според типа на атрибута.
Например:
Конфигуриран тип	Преобразуване	Допълнителна проверка
Integer	int.TryParse	Допустим диапазон
Decimal	decimal.TryParse	Положителна стойност, точност
Boolean	bool.TryParse	Разрешени стойности
Date	DateOnly.TryParse	Валиден период
Text	Няма числово преобразуване	Дължина, задължителност
Така нов атрибут от тип Decimal може да се обработва от общ механизъм, без да пишеш нов контролер за всяко поле.
За финансови стойности и количества с точност използвай подходящи типове като decimal, а не double, когато бизнес изискванията предполагат точна десетична аритметика.
4. ООП — общи договори, различно поведение
Тук стигаме до най-интересната част.
В твоята система някои операции са общи, но правилата за тях могат да се различават.
Например:
•	материал не може да бъде изписан в количество, по-голямо от наличното;
•	оборудване не може да бъде преместено, ако е изведено от употреба;
•	лекарство не може да бъде отпуснато след срока си на годност.
Вместо един огромен клас с десетки if проверки можеш да дефинираш общ договор за валидиране:
csharp

}
След това различни реализации могат да прилагат различни правила.

Има обаче една архитектурна подробност: IMovementValidator<TMovement> е подходящ, когато движенията са отделни типове, известни при компилация. Ако потребителят може да създава нови видове движения само чрез конфигурация, ще ти е необходим и модел за динамични правила. Не бих се опитвал да използвам Generics навсякъде само защото са подходящи на теория.
•	Generics — когато имаш общ алгоритъм или договор за различни типове.

3. Как бих моделирал това в C#?
Например можеш да имаш клас за описание на поле:

public enum FieldDataType
{
    Text,
    Integer,
    Decimal,
    Boolean,
    Date
}

public class FieldDefinition
{
    public int Id { get; set; }

    public string Name { get; set; } = string.Empty;

    public FieldDataType DataType { get; set; }

    public bool IsRequired { get; set; }

    public decimal? MinimumValue { get; set; }

    public decimal? MaximumValue { get; set; }

    public int? MaximumLength { get; set; }

Това е самото описание на поле, а не неговата конкретна стойност.

Тук имаш общ договор за преобразуване на стойности. Реализацията може да избира правилния парсер според DataType, а валидаторът да проверява задължителността, диапазоните и останалите ограничения.
Забележи нещо важно: FieldDefinition е обикновен C# клас. Не е необходимо системата да генерира нов C# клас за всяко поле, добавено от потребителя.
Това е една от най-големите ползи на този подход.
4. Но как ще съхраняваш самите стойности?
Тук започва истинското архитектурно предизвикателство.
Имаш два основни подхода.
Вариант А: метаданни плюс динамични стойности
Можеш да използваш таблици от типа:
•	ObjectDefinitions — видове обекти;
•	FieldDefinitions — определения на полетата;
•	ObjectInstances — конкретни обекти;
•	FieldValues — стойности на динамичните полета.
Например:
ObjectId	FieldDefinitionId	Value
101	Weight	12.50
101	ExpiryDate	2027-12-31
102	Weight	7.25
Това наподобява модел, известен като EAV (Entity-Attribute-Value).
Предимството е, че добавянето на ново поле не изисква нова колона в таблицата.
Недостатъкът е, че типизирането, заявките, ограниченията, индексите и отчетите стават по-сложни. Ако всички стойности се пазят в една текстова колона, ще трябва внимателно да решиш как се гарантират типовете и как се изпълняват сравненията.
Вариант Б: метаданни плюс JSON
Можеш да пазиш динамичните атрибути в JSON документ:
json
{
  "weight": 12.5,
  "expiryDate": "2027-12-31",
  "isActive": true
}
Това е удобно, когато различните обекти имат различни полета.
Но JSON сам по себе си не гарантира, че стойността отговаря на конфигурацията. C# кодът трябва да валидира данните, а ако използваш релационна база, трябва да обмислиш как ще индексираш и търсиш често използваните атрибути.
Какво бих избрал?
За твоята идея бих започнал с метаданни плюс ясно типизирано ядро, а динамичните атрибути бих съхранявал отделно, вероятно в JSON, ако използваната база данни и нуждите от заявки го позволяват.
Не бих използвал EAV за абсолютно всички данни. Основните понятия като документ, движение, местоположение, количество и идентификатор е по-добре да останат ясно моделирани.

•	Конфигурация: кое движение е разрешено, какви полета изисква и какви ограничения има.

Първото може да бъде силно конфигурируемо. Второто трябва да бъде контролирано от надежден код.
Не бих позволил потребителят да въвежда произволен C# код или SQL в таблица, за да определя как се движат данните. Това би създало сериозни рискове за сигурността и поддръжката.

•	форма за създаване на лекарство;
•	проверки за валидност на атрибутите;
•	списък с разрешени движения;
•	история на операциите;
•	справки за наличности.
Без да добавяш нов контролер, нова форма и нова таблица за всяко поле.
Това е реалната стойност на metadata-driven подхода.
Има обаче една граница: ако лекарствата изискват специфични правила за партиди, проследяване на срокове и блокиране на изтекли количества, може да ти трябва специализиран модул. Универсалната конфигурация не е заместител на всяка възможна бизнес логика.
