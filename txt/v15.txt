3. А за try-catch — тук има важно разграничение
Твоята идея:
„да направим файл или нещо където да хваща грешки и да ги показва като try-catch“
е добра като посока, но не бихме сложили един огромен try-catch навсякъде.
Има два различни типа проблеми:
Validation error
Потребителят е въвел нещо неправилно:
Age = 150
Това не е exception.
Тук използваме:
Validation
   ↓
ModelState
   ↓
Validation message
Неочаквана грешка
Например:
Database connection failed
или:
SQL Server is unavailable
Това вече е exception и там можем да използваме обработка на грешки.
Архитектурно бихме искали нещо подобно:
                    Request
                       ↓
                  Controller
                       ↓
                    Service
                       ↓
                    EF Core
                       ↓
                   Database
                       │
              ┌────────┴────────┐
              │                 │
          Validation        Exception
              │                 │
              ↓                 ↓
       User message       Error handling
                                ↓
                         Log + friendly
                           error page

7. Age validation — текущото състояние
Създадена е:
Common/Constants/StudentConstants.cs
с:
public static class StudentConstants
{
    public const int MinAge = 18;
    public const int MaxAge = 100;
}
CreateStudentViewModel използва:
[Range(StudentConstants.MinAge, StudentConstants.MaxAge,
    ErrorMessage = ValidationMessages.AgeMustBeBetweenMinAndMax)]
public int Age { get; set; }
Създадена е:
Common/Validation/ValidationMessages.cs
В момента:
public static class ValidationMessages
{
    public const string AgeMustBeBetweenMinAndMax =
        "Age must be between 18 and 100.";
}

8. Важният въпрос за утре
Това е първото нещо, което трябва да обсъдим.
В момента имаме дублиране:
StudentConstants
├── MinAge = 18
└── MaxAge = 100

ValidationMessages
└── "Age must be between 18 and 100."
Идеята ни е:
Ако дадена стойност може да се използва повече от веднъж, да я изнесем в константа, метод или друга подходяща abstraction, за да не я променяме на много места.
Опитахме:
"Age must be between {0} and {1}."
но [Range] интерпретира {0} и {1} по свой начин и получихме:
Age must be between Age and 18.
След това опитахме dynamic/static property, но получихме compiler error:
An attribute argument must be a constant expression,
typeof expression or array creation expression of an attribute parameter type
Опитахме и interpolated const string, но отново не беше прието като Attribute argument.
Затова върнахме проекта до работещо състояние.
Утре:
Да разгледаме спокойно вариантите за премахване на дублирането на 18 и 100, като:
o	запазим стандартния ASP.NET Core [Range], ако е възможно;
o	не създаваме custom validation attribute без реална необходимост;
o	не усложняваме излишно V1;
o	изберем архитектурно чисто решение.
Не започваме веднага с код. Първо обсъждаме вариантите.

9. Тестване до момента
Тествахме Create формата.
Примерни записани студенти:
hope | yv | esp_nv@abv.bg | Computer Science | 21
Ivan | Петров | ivan.petrov@example.com | Computer Science | 0
asdr | 7 | esp_nv@abv.bg | Computer Science | 1
Това показа, че преди добавянето на [Range] Age = 0 и Age = 1 са могли да бъдат записани.
След добавянето на [Range]:
Age = 17
се валидира правилно и студентът не се записва.
Последният тест показа съобщението:
Age must be between Age and 18.
След корекцията на ValidationMessages проектът е върнат в работещо състояние, но финалният тест на съобщението трябва да се направи след решението за централизиране.

11. Как работим по проекта
Това е важно и трябва да се запази.
Правило 1 — малки стъпки
1 малка промяна
      ↓
обяснение
      ↓
потребителят я прави
      ↓
Build
      ↓
проверка
      ↓
следваща стъпка
Не правим 10 промени наведнъж.
Правило 2 — не гадаем кода
Ако трябва да променим съществуващ файл:
Потребителят изпраща актуалния код
        ↓
разглеждаме го
        ↓
даваме конкретната промяна
Правило 3 — обяснение
Потребителят има малко HTML/CSS и Bootstrap знания и е виждал JavaScript, но досега често е използвал готов JS код без да го разбира напълно.
Затова при JavaScript трябва да се обяснява:
o	какво прави;
o	защо го използваме;
o	къде се поставя;
o	как работи;
o	как се свързва с HTML;
o	как се свързва с ASP.NET Core.
Не просто да се дава готов код за копиране.
Правило 4 — обяснението е под кода
Например:
var student = await _studentService.GetByIdAsync(id);
→ Service-ът търси студента по неговото ID.
Не натъпкваме обяснението като коментари вътре в кода.
Правило 5 — използваме схеми
При архитектурни и EF Core концепции:
Controller
    ↓
Service
    ↓
EF Core
    ↓
DbContext
    ↓
SQL Server
    ↓
Database
Правило 6 — Build след логична малка промяна
Търсим:
Errors: 0
Warnings: 0
преди следващата стъпка.
Правило 7 — преизползване
Ако нещо има реална вероятност да се използва повече от веднъж, първо обсъждаме дали да бъде:
o	метод;
o	константа;
o	helper;
o	shared class;
o	друга подходяща abstraction.
Но не правим abstraction само заради самия pattern.
