Стъпка 2: Как ще учим архитектурата
Искам да направим нещо малко по-различно от просто „копирай този код“.
За всеки клас ще си задаваме 3 въпроса:
1. Каква е неговата отговорност?
Например:
public class StudentsController : Controller
→ това е MVC Controller
→ приема HTTP заявки
→ извиква необходимата логика
→ връща View/резултат
2. Има ли този клас повече от една отговорност?
Ако например Controller-ът едновременно:
•	работи с database;
•	прави бизнес логика;
•	валидира;
•	преобразува Entity → ViewModel;
тогава вече имаме кандидат за refactoring.
3. Къде логично принадлежи тази отговорност?
Например:
Controller
    ↓
Service
    ↓
Repository
    ↓
DbContext
    ↓
Database
Това ще ни помогне да разберем SOLID, вместо просто да го използваме като термин.

3. StudentService.cs
Създай:
Services/StudentService.cs
със следното:
using Microsoft.EntityFrameworkCore;
using StudentManagement.Data;
using StudentManagement.Models;

namespace StudentManagement.Services;

public class StudentService : IStudentService
{
    private readonly ApplicationDbContext _context;

    public StudentService(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<List<Student>> GetAllAsync()
    {
        return await _context.Students
            .AsNoTracking()
            .ToListAsync();
    }

    public async Task<Student?> GetByIdAsync(int id)
    {
        return await _context.Students
            .FindAsync(id);
    }

    public async Task CreateAsync(Student student)
    {
        _context.Students.Add(student);
        await _context.SaveChangesAsync();
    }

    public async Task<bool> UpdateAsync(Student student)
    {
        var existingStudent = await _context.Students
            .FindAsync(student.Id);

        if (existingStudent == null)
        {
            return false;
        }

        existingStudent.FirstName = student.FirstName;
        existingStudent.LastName = student.LastName;
        existingStudent.Email = student.Email;
        existingStudent.Course = student.Course;
        existingStudent.Age = student.Age;

        await _context.SaveChangesAsync();

        return true;
    }

    public async Task<bool> DeleteAsync(int id)
    {
        var student = await _context.Students
            .FindAsync(id);

        if (student == null)
        {
            return false;
        }

        _context.Students.Remove(student);

        await _context.SaveChangesAsync();

        return true;
    }
}
Защо UpdateAsync е написан така?
В стария код имаме:
_context.Update(student);
await _context.SaveChangesAsync();
Това директно attach-ва получения от HTTP request обект и маркира неговите стойности за update. G GitHub
При рефакторирането е по-добре първо да намерим съществуващия запис:
var existingStudent = await _context.Students.FindAsync(student.Id);
и след това изрично да прехвърлим позволените properties.
Това ще ни даде и много по-добра основа по-късно да въведем DTO/ViewModel, вместо директно да приемаме database entity от POST request.

4. Регистрираме service-а в Program.cs
В текущия Program.cs вече имаме регистрация на ApplicationDbContext и MVC controllers. G GitHub
Добави:
using StudentManagement.Services;
и след:
builder.Services.AddControllersWithViews();
добави:
builder.Services.AddScoped<IStudentService, StudentService>();
Получава се:
using Microsoft.EntityFrameworkCore;
using StudentManagement.Data;
using StudentManagement.Services;

namespace StudentManagement
{
    public class Program
    {
        public static void Main(string[] args)
        {
            var builder = WebApplication.CreateBuilder(args);

            builder.Services.AddDbContext<ApplicationDbContext>(options =>
                options.UseSqlServer(
                    builder.Configuration.GetConnectionString("DefaultConnection")));

            builder.Services.AddControllersWithViews();

            builder.Services.AddScoped<IStudentService, StudentService>();

            var app = builder.Build();

            if (!app.Environment.IsDevelopment())
            {
                app.UseExceptionHandler("/Home/Error");
                app.UseHsts();
            }

            app.UseHttpsRedirection();
            app.UseStaticFiles();

            app.UseRouting();

            app.UseAuthorization();

            app.MapControllerRoute(
                name: "default",
                pattern: "{controller=Home}/{action=Index}/{id?}");

            app.Run();
        }
    }
}

5. Рефакторираме StudentsController
Сега идва съществената част.
Вместо:
private readonly ApplicationDbContext _context;
ще имаме:
private readonly IStudentService _studentService;
Целият StudentsController става:
using Microsoft.AspNetCore.Mvc;
using StudentManagement.Models;
using StudentManagement.Services;

namespace StudentManagement.Controllers;

public class StudentsController : Controller
{
    private readonly IStudentService _studentService;

    public StudentsController(IStudentService studentService)
    {
        _studentService = studentService;
    }

    public async Task<IActionResult> Index()
    {
        var students = await _studentService.GetAllAsync();

        return View(students);
    }

    public IActionResult Create()
    {
        return View();
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(Student student)
    {
        if (!ModelState.IsValid)
        {
            return View(student);
        }

        await _studentService.CreateAsync(student);

        return RedirectToAction(nameof(Index));
    }

    public async Task<IActionResult> Edit(int? id)
    {
        if (id == null)
        {
            return NotFound();
        }

        var student = await _studentService.GetByIdAsync(id.Value);

        if (student == null)
        {
            return NotFound();
        }

        return View(student);
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Edit(int id, Student student)
    {
        if (id != student.Id)
        {
            return NotFound();
        }

        if (!ModelState.IsValid)
        {
            return View(student);
        }

        var updated = await _studentService.UpdateAsync(student);

        if (!updated)
        {
            return NotFound();
        }

        return RedirectToAction(nameof(Index));
    }

    public async Task<IActionResult> Delete(int? id)
    {
        if (id == null)
        {
            return NotFound();
        }

        var student = await _studentService.GetByIdAsync(id.Value);

        if (student == null)
        {
            return NotFound();
        }

        return View(student);
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> DeleteConfirmed(int id)
    {
        var deleted = await _studentService.DeleteAsync(id);

        if (!deleted)
        {
            return NotFound();
        }

        return RedirectToAction(nameof(Index));
    }
}
Какво спечелихме?
Преди:
Controller
 ├── MVC logic
 ├── validation
 ├── EF Core queries
 ├── database updates
 └── database deletes
След:
Controller
 └── HTTP/MVC logic

IStudentService
 └── contract

StudentService
 └── student business/data operations

ApplicationDbContext
 └── EF Core/database
Това вече е реален рефакторинг, а не просто преместване на код.

Какво направихме?
Този клас е мястото, където ще се намира логиката за работа със студентите.
Например:
GetAllAsync()
взема всички студенти от базата.
GetByIdAsync(int id)
търси конкретен студент.
CreateAsync(Student student)
добавя нов студент.
UpdateAsync(Student student)
променя съществуващ студент.
DeleteAsync(int id)
изтрива студент.
Важното на този етап
Този ред:
private readonly ApplicationDbContext _context;
означава, че StudentService използва нашия ApplicationDbContext, за да разговаря с базата данни.

Най-важната част
Тук:

    .FindAsync(student.Id);
ние взимаме съществуващия Student от базата.
EF Core започва да го следи:
Student
   ↓
Unchanged
След това правим:
existingStudent.FirstName = student.FirstName;
и същото за останалите properties.
EF Core забелязва:
Unchanged
    ↓
Modified
И когато изпълним:
await _context.SaveChangesAsync();
EF Core знае, че този обект е променен и изпраща UPDATE към базата.
Защо не правим просто това?
_context.Update(student);
Това беше старият вариант в контролера.
И той работи, но при нашето рефакториране предпочитаме:
Получаваме Student от DB
        ↓
EF Core го tracking-ва
        ↓
Променяме позволените properties
        ↓
SaveChangesAsync()
Това ни дава по-добър контрол върху това какво точно променяме.

Защо хората използват Repository?
Има няколко основни причини.
1. Separation of Concerns
Разделяме:
Service
↓
Business logic
от:
Repository
↓
Data access
Например след време може да имаме логика:
StudentService
│
├── проверява дали студентът може да бъде записан
├── проверява дали email-ът е уникален
├── изчислява нещо
└── използва Repository за database operations
Repository отговаря само за:
„Как да взема/запиша данните?“
________________________________________
2. По-лесно тестване
Представи си, че искаме да тестваме:
StudentService
без реална база.
Можем да дадем фалшив Repository:
              StudentService
                   │
                   ▼
          IStudentRepository
             /          \
            /            \
      реален             fake
    Repository         Repository
        │                  │
        ▼                  ▼
    Database          Test data
Така можем да тестваме Service-а без SQL Server.
________________________________________
3. Можем да сменим data source
Теоретично:
IStudentRepository
       │
       ├── StudentRepository
       │       ↓
       │    SQL Server
       │
       ├── MongoStudentRepository
       │       ↓
       │     MongoDB
       │
       └── ApiStudentRepository
               ↓
             REST API
Service-ът не трябва да знае какво има отдолу.

Стъпка 2: Как ще учим архитектурата
Искам да направим нещо малко по-различно от просто „копирай този код“.
За всеки клас ще си задаваме 3 въпроса:
1. Каква е неговата отговорност?
Например:
public class StudentsController : Controller
→ това е MVC Controller
→ приема HTTP заявки
→ извиква необходимата логика
→ връща View/резултат
2. Има ли този клас повече от една отговорност?
Ако например Controller-ът едновременно:
o	работи с database;
o	прави бизнес логика;
o	валидира;
o	преобразува Entity → ViewModel;
тогава вече имаме кандидат за refactoring.
3. Къде логично принадлежи тази отговорност?
Например:
Controller
    ↓
Service
    ↓
Repository
    ↓
DbContext
    ↓
Database
Това ще ни помогне да разберем SOLID, вместо просто да го използваме като термин.

3. StudentService.cs
Създай:
Services/StudentService.cs
със следното:
using Microsoft.EntityFrameworkCore;
using StudentManagement.Data;
using StudentManagement.Models;

namespace StudentManagement.Services;

public class StudentService : IStudentService
{
    private readonly ApplicationDbContext _context;

    public StudentService(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<List<Student>> GetAllAsync()
    {
        return await _context.Students
            .AsNoTracking()
            .ToListAsync();
    }

    public async Task<Student?> GetByIdAsync(int id)
    {
        return await _context.Students
            .FindAsync(id);
    }

    public async Task CreateAsync(Student student)
    {
        _context.Students.Add(student);
        await _context.SaveChangesAsync();
    }

    public async Task<bool> UpdateAsync(Student student)
    {
        var existingStudent = await _context.Students
            .FindAsync(student.Id);

        if (existingStudent == null)
        {
            return false;
        }

        existingStudent.FirstName = student.FirstName;
        existingStudent.LastName = student.LastName;
        existingStudent.Email = student.Email;
        existingStudent.Course = student.Course;
        existingStudent.Age = student.Age;

        await _context.SaveChangesAsync();

        return true;
    }

    public async Task<bool> DeleteAsync(int id)
    {
        var student = await _context.Students
            .FindAsync(id);

        if (student == null)
        {
            return false;
        }

        _context.Students.Remove(student);

        await _context.SaveChangesAsync();

        return true;
    }
}
Защо UpdateAsync е написан така?
В стария код имаме:
_context.Update(student);
await _context.SaveChangesAsync();
Това директно attach-ва получения от HTTP request обект и маркира неговите стойности за update. G GitHub
При рефакторирането е по-добре първо да намерим съществуващия запис:
var existingStudent = await _context.Students.FindAsync(student.Id);
и след това изрично да прехвърлим позволените properties.
Това ще ни даде и много по-добра основа по-късно да въведем DTO/ViewModel, вместо директно да приемаме database entity от POST request.

namespace StudentManagement

            var builder = WebApplication.CreateBuilder(args);

5. Рефакторираме StudentsController
Сега идва съществената част.
Вместо:
private readonly ApplicationDbContext _context;
ще имаме:
private readonly IStudentService _studentService;
Целият StudentsController става:
using Microsoft.AspNetCore.Mvc;
using StudentManagement.Models;
using StudentManagement.Services;

namespace StudentManagement.Controllers;

public class StudentsController : Controller
{
    private readonly IStudentService _studentService;

    public StudentsController(IStudentService studentService)
    {
        _studentService = studentService;
    }

    public async Task<IActionResult> Index()
    {
        var students = await _studentService.GetAllAsync();

        return View(students);
    }

    public IActionResult Create()
    {
        return View();
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Create(Student student)
    {
        if (!ModelState.IsValid)
        {
            return View(student);
        }

        await _studentService.CreateAsync(student);

        return RedirectToAction(nameof(Index));
    }

    public async Task<IActionResult> Edit(int? id)
    {
        if (id == null)
        {
            return NotFound();
        }

        var student = await _studentService.GetByIdAsync(id.Value);

        if (student == null)
        {
            return NotFound();
        }

        return View(student);
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> Edit(int id, Student student)
    {
        if (id != student.Id)
        {
            return NotFound();
        }

        if (!ModelState.IsValid)
        {
            return View(student);
        }

        var updated = await _studentService.UpdateAsync(student);

        if (!updated)
        {
            return NotFound();
        }

        return RedirectToAction(nameof(Index));
    }

    public async Task<IActionResult> Delete(int? id)
    {
        if (id == null)
        {
            return NotFound();
        }

        var student = await _studentService.GetByIdAsync(id.Value);

        if (student == null)
        {
            return NotFound();
        }

        return View(student);
    }

    [HttpPost]
    [ValidateAntiForgeryToken]
    public async Task<IActionResult> DeleteConfirmed(int id)
    {
        var deleted = await _studentService.DeleteAsync(id);

        if (!deleted)
        {
            return NotFound();
        }

        return RedirectToAction(nameof(Index));
    }
}

using Microsoft.EntityFrameworkCore;
using StudentManagement.Data;
using StudentManagement.Models;

namespace StudentManagement.Services;

public class StudentService : IStudentService
{
    private readonly ApplicationDbContext _context;

    public StudentService(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task<List<Student>> GetAllAsync()
    {
        return await _context.Students
            .AsNoTracking()
            .ToListAsync();
    }

    public async Task<Student?> GetByIdAsync(int id)
    {
        return await _context.Students.FindAsync(id);
    }

    public async Task CreateAsync(Student student)
    {
        _context.Students.Add(student);
        await _context.SaveChangesAsync();
    }

    public async Task<bool> UpdateAsync(Student student)
    {
        var existingStudent = await _context.Students
            .FindAsync(student.Id);

        if (existingStudent == null)
        {
            return false;
        }

        existingStudent.FirstName = student.FirstName;
        existingStudent.LastName = student.LastName;
        existingStudent.Email = student.Email;
        existingStudent.Course = student.Course;
        existingStudent.Age = student.Age;

        await _context.SaveChangesAsync();

        return true;
    }

    public async Task<bool> DeleteAsync(int id)
    {
        var student = await _context.Students.FindAsync(id);

        if (student == null)
        {
            return false;
        }

        _context.Students.Remove(student);
        await _context.SaveChangesAsync();

        return true;
    }
}
Какво направихме?

изтрива студент.

Unchanged

Какво е Repository?
Най-просто казано, Repository е слой, който отговаря за достъпа до данните.
В нашия проект в момента StudentService сам говори с EF Core:
┌──────────────────────┐

           │
           ▼
┌──────────────────────┐

└──────────────────────┘
Ако използваме Repository, ще стане:
┌──────────────────────┐
│ StudentsController   │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│   StudentService     │
│                      │
│ бизнес логика        │
└──────────┬───────────┘
           │
           │ IStudentRepository
           ▼
┌──────────────────────┐
│  StudentRepository   │
│                      │
│ _context.Students    │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐

└──────────┬───────────┘
           │
           ▼

Как изглежда това на практика?
Например Repository интерфейсът може да бъде:
public interface IStudentRepository
{
    Task<List<Student>> GetAllAsync();

    Task<Student?> GetByIdAsync(int id);

    Task AddAsync(Student student);

    Task UpdateAsync(Student student);

    Task DeleteAsync(Student student);
}
Той казва:
„Това са операциите, които мога да извършвам върху Student в data layer-а.“
После имаме:
public class StudentRepository : IStudentRepository
{
    private readonly ApplicationDbContext _context;

    public StudentRepository(ApplicationDbContext context)
    {
        _context = context;
    }

    // database operations...
}
Тук вече живее EF Core кодът.

А какво прави Service?
Тогава StudentService ще работи с Repository:
StudentService
      │
      │ IStudentRepository
      ▼

      │
      │ ApplicationDbContext
      ▼
   EF Core
      │
      ▼

Например:
public async Task CreateAsync(Student student)
{

}
Това на пръв поглед изглежда почти прекалено просто.

Имаме ли реална полза от този допълнителен слой?
________________________________________
Защо хората използват Repository?
Има няколко основни причини.
1. Separation of Concerns
Разделяме:
Service
↓
Business logic
от:
Repository
↓
Data access
Например след време може да имаме логика:
StudentService
│
├── проверява дали студентът може да бъде записан
├── проверява дали email-ът е уникален
├── изчислява нещо
└── използва Repository за database operations
Repository отговаря само за:
„Как да взема/запиша данните?“
________________________________________
2. По-лесно тестване
Представи си, че искаме да тестваме:
StudentService
без реална база.
Можем да дадем фалшив Repository:
              StudentService
                   │
                   ▼
          IStudentRepository
             /          \
            /            \
      реален             fake
    Repository         Repository
        │                  │
        ▼                  ▼
    Database          Test data
Така можем да тестваме Service-а без SQL Server.
________________________________________
3. Можем да сменим data source
Теоретично:
IStudentRepository
       │
       ├── StudentRepository
       │       ↓
       │    SQL Server
       │
       ├── MongoStudentRepository
       │       ↓
       │     MongoDB
       │
       └── ApiStudentRepository
               ↓
             REST API
Service-ът не трябва да знае какво има отдолу.
________________________________________
Но има един много важен проблем
В нашия проект използваме Entity Framework Core.
А EF Core вече предоставя много от функционалността, която Repository Pattern се опитва да абстрахира.
Имаме:
_context.Students
което вече е:
DbSet<Student>
и ни дава:
o	LINQ заявки
o	FindAsync
o	FirstOrDefaultAsync
o	ToListAsync
o	Add
o	Remove
o	Change Tracking
o	Transactions
o	SaveChangesAsync
Затова ако направим Repository, което просто препраща тези методи:
StudentService
     ↓
Repository
     ↓
DbContext
може реално да сме създали излишен слой.
________________________________________
Пример за излишна абстракция
Може да се получи нещо такова:
public async Task<List<Student>> GetAllAsync()
{
    return await _repository.GetAllAsync();
}
Repository:
public async Task<List<Student>> GetAllAsync()
{
    return await _context.Students.ToListAsync();
}
Виждаш ли проблема?
Имаме:
Controller
   ↓
Service
   ↓
Repository
   ↓
DbContext
но Service-ът не прави нищо допълнително.
Само препраща:
GetAllAsync()
      ↓
GetAllAsync()
      ↓
ToListAsync()
Това увеличава кода и броя файлове, без да добавя много стойност.
________________________________________
А кога Repository вече има смисъл?
Например ако имаме по-сложна система:
StudentService
      │
      ▼
IStudentRepository
      │
      ├── GetActiveStudentsAsync()
      ├── GetStudentsByCourseAsync()
      ├── GetStudentsWithGradesAsync()
      ├── SearchAsync(...)
      └── GetStudentsEligibleForScholarshipAsync()
Тогава Repository-то може да съдържа сложни query-та.
Например:
GetStudentsEligibleForScholarshipAsync()
                 │
                 ▼
        ┌────────────────┐
        │ StudentRepository
        └───────┬────────┘
                │
                ▼
        сложна EF Core
           LINQ заявка
                │
                ▼
            SQL Server
Тук вече имаме по-сериозна причина за отделен data-access layer.
________________________________________

┌──────────────────────┐

└──────────┬───────────┘

           ▼
┌──────────────────────┐
│   IStudentService    │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│   StudentService     │
│                      │
│ Business logic       │

Причината не е, че Repository Pattern е лош.
Напротив — той е полезен pattern.
Просто не трябва да използваме design pattern само защото е design pattern.
За нашия малък StudentManagement в момента Service + EF Core е напълно разумна архитектура.
