       ↓

       ↓
EF Core
       ↓

Рефакторирахме го до:

       ↓

       ↓

       ↓

       ↓

       ↓

CRUD операциите вече са в StudentService:
GetAllAsync()
GetByIdAsync()
CreateAsync()
UpdateAsync()
DeleteAsync()
Разгледахме подробно как EF Core работи при:
o	Add()
o	SaveChangesAsync()
o	FindAsync()
o	Update
o	Remove()
o	Change Tracking
o	Unchanged
o	Modified
o	Deleted
Разгледахме и защо:

не означава автоматично, че записът вече е направен в DB.
Реалното записване става при:
await _context.SaveChangesAsync();

4. Решения, които взехме
Service Pattern — ДА
Използваме:
Controller
    ↓
IStudentService
    ↓
StudentService
Целта е Controller-ът да не съдържа database/business logic.
Интерфейси — отделна папка
Избрахме:
Services
└── Interfaces
Това е нарочно, за да бъде структурата ясна.
Repository Pattern — ЗАСЕГА НЕ
Обсъдихме подробно Repository Pattern.
Решението ни е:
Не добавяме Repository само заради самия pattern.
Причината е, че проектът е сравнително малък и EF Core вече предоставя силна data-access abstraction чрез DbContext/DbSet.
Ако проектът порасне или се появи реална необходимост, можем да го добавим по-късно.
CSV/TXT — отделна функционалност
Ако някой ден искаме:
Database
   ↓
CSV/TXT
не е задължително да използваме Repository.
По-логично е да имаме отделна export функционалност/service.
MySQL/друга DB
Ако някой ден сменим SQL Server с MySQL, първо ще преценим нуждата от Repository според реалната архитектура.
EF Core позволява използването на различни database providers, така че Repository не е автоматично необходим.

5. Как пишем проекта
Това е много важно и утре трябва да продължим по същия начин.
Правило №1 — стъпка по стъпка
Не даваме 10 промени наведнъж.
Правим:
1 малка промяна
      ↓
обяснение
      ↓
потребителят я прави
      ↓
Build
      ↓
проверка
      ↓
следваща стъпка
Правило №2 — не гадаем кода
Ако трябва да променим съществуващ файл:
Първо потребителят го изпраща → разглеждаме реалния код → после даваме промяна.
Особено важно за:
Controller
Service
View
ViewModel
DbContext
Правило №3 — начинаещо ниво
Обясняваме:
o	какво прави кодът;
o	защо го правим;
o	кой слой отговаря за него;
o	какво се случва с данните;
o	как EF Core комуникира с DB.
Не просто:
„Копирай този код.“
Правило №4 — коментари под кода
Когато обясняваме код:
var student = await _studentService.GetByIdAsync(id);
обяснението е под кода, а не чрез наблъскване на коментари вътре:
var student = await _studentService.GetByIdAsync(id);
→ Service-ът търси студента по неговото ID.
Правило №5 — използваме блок-схеми
Когато има архитектурна или EF Core концепция, използваме схема:
Controller
    ↓
Service
    ↓
EF Core
    ↓
DbContext
    ↓
SQL Server
    ↓
Database
При нужда правим по-подробна схема с конкретните методи:
Create()
   ↓
CreateAsync()
   ↓
DbSet.Add()
   ↓
Change Tracker
   ↓
SaveChangesAsync()
   ↓
SQL INSERT
   ↓
Database
Правило №6 — Build след логична малка промяна
Търсим:
Errors: 0
Warnings: 0
и чак тогава продължаваме.
Правило №7 — сигурност
По време на рефакторирането обръщаме внимание на:
✓ SQL Injection
✓ Validation
✓ Whitespace
✓ MaxLength
✓ XSS
✓ Mass Assignment
✓ CSRF
✓ Authorization
✓ Database constraints
Вече обсъдихме, че EF Core параметризира нормалните LINQ заявки и не трябва да сглобяваме SQL чрез string concatenation.
