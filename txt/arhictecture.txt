Архитектура на системата — текущо състояние
Основен принцип
Системата няма да бъде направена само за програмиране или конкретна област.
Тя трябва да може да се използва за:
•	програмиране;
•	езици;
•	математика;
•	бизнес;
•	други видове обучения.
Тоест областта на обучение не е част от основната архитектура.
________________________________________
V1 — Основна версия
V1 представлява общата картина на обучителната система.
До момента сме завършили три основни концепции:
V1
│
├── Student / Студент       ✅
├── Teacher / Преподавател  ✅
└── Course / Курс           ✅
1. Student / Студент ✅
За студента трябва да можем да виждаме какво се случва с неговото обучение по конкретен курс.
Информация за курса
Студентът може да бъде:
•	записан;
•	обучаващ се;
•	завършил;
•	отказал се/прекратил.
Progress / Напредък
Във V1 е обобщена стойност:
7 / 10
70%
и можем да покажем:
Remaining:
3 / 10
Attendance / Присъствие
Отделно от прогреса:
7 / 10
70%
Това е важно:
Progress ≠ Attendance
Студентът може например да има:
Progress:    70%
Attendance:  90%
Оценки
Пазим:
Intermediate Grade / Междинна оценка
Final Grade / Крайна оценка
Във V1 те са обобщени стойности.
В V2 ще можем да изградим детайлна система за оценяване и част от тези стойности да станат изчисляеми.

2. Teacher / Преподавател ✅
Преподавателят е самостоятелна концепция.
Не го обвързваме директно с един курс.
Избрахме:
Teacher
   │
   │ N:M
   ▼
TeacherCourseInstance
   │
   ▼
CourseInstance
Тоест:
•	един преподавател може да води много провеждания;
•	едно провеждане може да има повече от един преподавател.
Пример:
Иван
 ├── C# — 2026
 ├── Python — 2026
 └── C# Advanced — 2027

Мария
 ├── C# — 2027
 └── JavaScript — 2027
Какво НЕ правим във V1
Не записваме още:
„Иван е преподавал тема LINQ.“
Това остава за V2, когато въведем теми и занятия.

3. Course / Курс ✅
Тук направихме най-много уточнения.
Основната идея е:
V1 Course е визитна карта на курса + обща информация за конкретното му провеждане и студентите.

Самият курс съдържа обща информация:

Description / Описание

2. Classes

Това е V2.

        ↓

3. Роли — V1
Имаме 5 роли:
                    USER
                      │
       ┌──────────────┼──────────────┐
       │              │              │
 System Admin      Admin          Manager
                                      │
                              ┌───────┴───────┐
                              │               │

Функционално ги разграничихме така:
Роля	Основна отговорност
System Administrator	Състояние и поддръжка на системата
Administrator	Роли, права и достъп
Manager	Управление на курсове и участници
Teacher	Обучение, присъствие и оценки
Student	Участие и собствено обучение

5. Administrator
Основната му функция е управление на достъпа.
Administrator
       │
       ├── Users
       │
       ├── Roles
       │
       ├── Permissions
       │
       └── Access to Forms / Functions
Например:
Teacher
   │
   ├── View Course       ✓
   ├── Attendance        ✓
   ├── Grades            ✓
   └── Edit Course       ✗
UI:
Permission = TRUE
       ↓
показва се функцията
Permission = FALSE
       ↓
скрива се функцията
       +
сървърът блокира достъпа
Важно: скриването на линк не е механизъм за сигурност. Правата трябва да се проверяват и на ниво backend.
V2
Оставяме:
Role Permissions
        +
Individual User Permissions

6. Manager

   │

   │

Manager определя основните параметри на курса:

├── Description
├── Requirements
├── Level
├── Language
├── Topics Count
├── Year
├── Capacity
├── Delivery Type
└── Days / Time period

Manager
   │
   └── Assign Teacher
             ↓
          Course
Manager вижда учебната информация, но не въвежда оценките и присъствието.

Финално състояние на архитектурата
В момента имаме доста добра основа:
V1 = Course-centered system / Система, центрирана около курсовете
с:
o	5 роли;
o	ясни основни права;
o	Course ↔ Student;
o	Course ↔ Teacher;
o	прогрес;
o	присъствие;
o	оценки;
o	записване;
o	UI настройки;
o	системен статус;
o	проста permission система;
o	ясна граница V1/V2/V3.
И най-важното решение, което според мен трябва да запазим като водещ принцип:
Не добавяме функционалност само защото технически можем. Добавяме я, когато реално е необходима.
Това ще ни помогне V1 да остане малка, разбираема, стабилна и лесна за разширяване.
