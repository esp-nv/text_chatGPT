CourseOffering е свързан с конкретен Course.

При четене се използва Include(co => co.Course), така че UI да може да показва информацията за свързания Course.

Потвърдено е, че soft-deleted Course не трябва да се използва като нормално активно CourseOffering.

CourseOffering Soft Delete
Продължихме същия soft delete подход, използван при Course.

CourseOffering не се премахва физически от базата.

При Delete:

`IsDeleted = true`

След това нормалните queries филтрират:

`!co.IsDeleted`

По този начин историческите данни остават в базата.

Това е важно за бъдещите Enrollment записи и историческата информация за проведени курсове.

CourseOffering Validation
Добавихме validation за основните времеви зависимости.

Проверяват се:

`EndDate >= StartDate`

`EnrollmentEndDate >= EnrollmentStartDate`

`EnrollmentStartDate <= StartDate`

Тези проверки са реализирани във ViewModel чрез IValidatableObject.

Проверихме през UI, че при невалидни дати формата не се записва и validation messages се показват на потребителя.

DateTime и Required
Днес открихме важна особеност при DateTime.

DateTime като value type винаги има стойност и когато потребителят не е въвел дата, стойността може да бъде:

`01.01.0001`

Затова [Required] върху:

`DateTime`

не дава поведението, което очакваме за празно UI поле.

За ViewModel-а преминахме към:

`DateTime?`

и запазихме [Required].

Validation логиката беше направена null-safe чрез HasValue.

Това позволи UI да показва правилно:

`The StartDate field is required.`

вместо да приема 01.01.0001 като реална дата.

Това беше полезен пример за разликата между value type и nullable value type при server-side validation.

CourseOffering UI
Проверихме CourseOffering през реалния UI.

Успешно бяха проверени:

Course selection;

Enrollment Start Date;

Enrollment End Date;

Capacity;

validation при невалидни дати;

validation при празни полета;

Create;

Edit;

Delete;

soft delete.

Проверихме и базата, за да потвърдим, че soft delete не премахва физически записа.

`Status = Active`

Предстои ViewModel-ът да бъде разширен с данните, необходими за избор на достъпни CourseOfferings.

Student Enrollment UI – решение
Обсъдихме как студентът ще използва Enrollment функционалността за тестови цели.

`Student Name + Email`

`Available Courses`

Основното правило е:

`CourseOffering.IsDeleted == false`

`Course.IsDeleted == false`

`EnrollmentStartDate <= current date`

`EnrollmentEndDate >= current date`

Вече записаните CourseOfferings за конкретния Student няма да се показват като нови възможности за записване.

Този flow е базов и може да бъде разширен по-късно според реалните business requirements.

Потвърдихме, че Enrollment също трябва да запазва историческите данни.

При бъдещо Cancel действие няма да изтриваме физически Enrollment записа.

Така системата може да запази информацията за предишното записване.

## CourseOffering Validation

Първоначално DateTime полетата бяха дефинирани като:

    `DateTime

с `[Required]`.

При тестване на Create UI се установи важен проблем:

`DateTime` е value type и има default стойност `01.01.0001`, поради което `[Required]` не може да различи празно поле от реално подадена дата.

Полетата бяха променени на nullable:

    `DateTime?
    `

като `[Required]` остава върху тях.

Validation логиката в `IValidatableObject` беше направена null-safe чрез `HasValue`.

Това доведе до правилно UI поведение при празна форма:

    `The StartDate field is required.
    The EndDate field is required.
    The EnrollmentStartDate field is required.
    The EnrollmentEndDate field is required.

CourseOffering Validation
При тестване на Create формата беше открит проблем с [Required] върху DateTime.

Първоначално полетата бяха:

DateTime StartDate
DateTime EndDate
DateTime EnrollmentStartDate
DateTime EnrollmentEndDate

Проблемът е, че DateTime е value type и при липса на стойност получава default:

01.01.0001

Поради това [Required] не може да третира полето като null.

Решението беше полетата във ViewModel-а да станат nullable:

DateTime?

като [Required] остана.

Validation логиката беше променена така, че първо да проверява дали стойностите съществуват.

Например:

StartDate.HasValue
EndDate.HasValue

Това предотвратява validation logic да се опитва да сравнява липсващи стойности.

CourseOffering Business Validation
В CourseOfferingViewModel е реализиран IValidatableObject.

Проверяват се:

EndDate >= StartDate

EnrollmentEndDate >= EnrollmentStartDate

EnrollmentStartDate <= StartDate

При нарушение се добавя конкретна ValidationResult към съответното поле.

Това беше тествано през UI.

Например при:

Start date: 05-Nov-2026
End date: 09-Feb-2026

се показва:

End date cannot be before start date.

При:

Enrollment start date: 15-Nov-2026
Start date: 05-Nov-2026

се показва:

Enrollment start date cannot be after course start date.

При:

Enrollment start date: 15-Nov-2026
Enrollment end date: 10-Nov-2026

се показва:

Enrollment end date cannot be before enrollment start date.

Невалидните данни не се записват.

Duplicate Enrollment
Не се допуска един Student да има повече от един активен/съществуващ Enrollment за същия CourseOffering.

При вече съществуващ запис CreatePendingAsync връща неуспешен резултат.

Това е business rule и затова проверката е в Service layer, а не само в UI.

Enrollment Approval
Реализирана е базова ApproveAsync логика.

Enrollment може да бъде одобрен само ако текущият статус е:

Pending

Преди промяна към Active се проверява CourseOffering.

След това се преброяват съществуващите Active Enrollments.
