1. Какво е EF Core?
EF Core (Entity Framework Core) е инструмент, който ни позволява да работим с Database (база данни) чрез C# objects (C# обекти), вместо постоянно сами да пишем SQL.
Най-просто:
C# приложение
     ↓
   EF Core
     ↓
   SQL
     ↓
 Database
Например имаме таблица:
Users
----------------
Id | Name | Age
----------------
1  | Ivan | 30
2  | Maria| 25
3  | Peter| 40
В C# можем да имаме:
class User
{
    public int Id { get; set; }
    public string Name { get; set; }
    public int Age { get; set; }
}
EF Core прави връзката:
Database Table          C# Class

Users            →      User
Id               →      Id
Name             →      Name
Age              →      Age
Това е основната идея.

2. Защо ни трябва EF Core?
Представи си, че искаме:
„Дай ми всички Users, които са над 30 години.“
Без EF Core можем да напишем SQL:
SELECT *
FROM Users
WHERE Age > 30;
С EF Core можем да изразим същата идея чрез C#:
var users = context.Users
    .Where(u => u.Age > 30);
Тук важното е да не учим кода наизуст.
Нека първо го разчетем.
context
   ↓
Users
   ↓
Where
   ↓
Age > 30
Тоест:
„Вземи Users от Database и остави само тези, при които Age е по-голямо от 30.“

Това е един от най-важните термини в EF Core.
DbContext → контекст към базата данни

        C#
         ↓
     DbContext
         ↓
      Database

„Този клас представлява връзката/контекста с Database.“

1. ORM — Object-Relational Mapping
Термините
Object → Обект
Relational → Релационен / свързан с релационна база данни
Mapping → Съпоставяне / свързване
Следователно:
ORM = Object-Relational Mapping
Най-просто:
ORM е начин да свържем C# objects (обекти) с таблици в Database (база данни).
Това е основната идея.
________________________________________
2. Защо изобщо ни трябва ORM?
Нека си представим, че имаме база данни.
В нея има таблица:

-------------------------

А в C# можем да имаме:

ЕТАП 2 — Проверявам как ще се направи Mapping
Тук имам 3 начина:
1. Convention / Auto Mapping
2. Attributes
3. Fluent API
________________________________________
1. Convention / Auto Mapping
Какво означава?
Оставям EF Core сам да направи mapping-а, когато имената и структурата следват неговите conventions.
Например:
C#                         Database

Product      ─────────→    Products

Id           ─────────→    Id
Name         ─────────→    Name
Price        ─────────→    Price
Ако всичко съвпада, може да не пиша никаква специална конфигурация.
Кога е най-удобен?
Използвам го, когато:
o	имената на Entity и Table са стандартни;
o	имената на Properties и Columns съвпадат;
o	нямам специални правила;
o	искам по-малко код.
Мисловно правило:
„Ако всичко е стандартно и съвпада → оставям EF Core сам да го разбере.“
________________________________________
2. Attributes
Ако имената не съвпадат, мога да използвам Attributes.
Например:
[Table("store_products")]
public class Product
{
    [Column("product_id")]
    public int Id { get; set; }

    [Column("product_name")]
    public string Name { get; set; }

    [Column("product_price")]
    public decimal Price { get; set; }
}
Тук казвам:
Product → store_products

Id    → product_id
Name  → product_name
Price → product_price
Кога са най-удобни?
Attributes са удобни, когато:
o	mapping-ът е сравнително прост;
o	искам да виждам mapping-а директно върху Entity-то;
o	имам малко конфигурация;
o	работя по малък/прост проект.
Мисловно правило:
„Искам да видя mapping-а директно върху property-то/класа → Attributes.“
________________________________________
3. Fluent API
При Fluent API не слагам mapping-а върху Entity класа.
Entity-то остава чисто:
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}
А mapping-ът е в OnModelCreating:
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>()
        .ToTable("store_products");

    modelBuilder.Entity<Product>()
        .Property(p => p.Id)
        .HasColumnName("product_id");

    modelBuilder.Entity<Product>()
        .Property(p => p.Name)
        .HasColumnName("product_name");

    modelBuilder.Entity<Product>()
        .Property(p => p.Price)
        .HasColumnName("product_price");
}
Получаваме:
Product → store_products

Id    → product_id
Name  → product_name
Price → product_price
Кога е най-удобен?
Fluent API е особено удобен, когато:
o	mapping-ът е по-сложен;
o	имам много configuration;
o	имам relationships;
o	имам keys и constraints;
o	искам configuration-ът да е отделен от Entity класа;
o	работя по по-голям проект;
o	искам всички правила за базата да са организирани на едно място.
Мисловно правило:
„Искам Entity-то да описва обекта, а configuration-ът да е отделно → Fluent API.“

🧱 9. Fluent API
При Fluent API държа Entity класа чист:
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
}
А configuration-а го пиша отделно:
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Product>()
        .ToTable("store_products");

    modelBuilder.Entity<Product>()
        .Property(p => p.Id)
        .HasColumnName("product_id");

    modelBuilder.Entity<Product>()
        .Property(p => p.Name)
        .HasColumnName("product_name");

    modelBuilder.Entity<Product>()
        .Property(p => p.Price)
        .HasColumnName("product_price");
}
Мисли:
Entity
 ↓
описва обекта


Fluent API
 ↓
описва как обектът се свързва с Database
Кога е най-удобен?
Особено когато:
o	mapping-ът е по-сложен;
o	имам много configuration;
o	имам relationships;
o	имам keys;
o	имам constraints;
o	искам configuration-ът да е отделен;
o	работя по по-голям проект.
Нашият избор
Разбираме и трите, но ще упражняваме основно Fluent API.

И чак тогава ще разгледаме алгоритмите по начина, който според мен ще ти е най-полезен:
Не само „това е алгоритъм“, а „какво реално прави компютърът стъпка по стъпка“.
Например:
Намираме число в масив:

[10, 25, 7, 80, 42]

Търсим 80
 ↓
проверяваме 10
 ↓
проверяваме 25
 ↓
проверяваме 7
 ↓
проверяваме 80
 ↓
намерено
Оттам естествено стигаме до:
o	Big O
o	O(1)
o	O(n)
o	O(log n)
o	arrays
o	lists
o	dictionaries
o	hash tables
o	sorting
o	searching
o	recursion
И после вече можем да свържем всичко с нещата, които учиш в C#:
Memory
   ↓
References / Objects
   ↓
Collections
   ↓
Algorithms
   ↓
LINQ
   ↓
EF Core
   ↓
Database
Така няма да учиш отделни парчета наизуст, а ще започнеш да виждаш как всичко работи „под капака“ и защо кодът, който пишеш, работи по този начин.
И бих го правил с теб точно както досега — една стъпка, един въпрос, проверка дали си го разбрала и чак тогава следващата.
